Agent First manifesto · Erica Love

AI transformation is a work-design problem.

The question is not where to insert AI into the workflow. The question is how the work should be divided between the human and the surrounding system—and only then what role AI should play.

EL
Erica Love
Founder, Agent First · Agent First Consulting

Organizations keep starting AI conversations with the technology. Which model should we use? Which tasks can we automate? Where can we add a copilot? What can an agent do?

Those are useful questions, but they are not first questions.

The first question is more basic: What is the person actually being asked to do, and why is the work designed that way?

In many operations, a surprising amount of “human work” is not judgment, empathy, creativity, or relationship-building. It is remembering which rule applies, searching for the current procedure, switching between systems, reconstructing context, translating policy into usable language, checking whether an exception exists, and figuring out what happens next.

We have mistaken the burden of navigating the system for the value of the human inside it.

That matters because a weak workflow does not become a strong workflow merely because an AI model is added to it. Sometimes AI simply becomes one more tab, one more place to check, or one more source of uncertainty that the worker must reconcile.

So my starting point is different: redesign the responsibility system before automating it.

Start with the work, not the model.

A job is not a list of tasks. It is a stream of decisions made inside a particular environment. The person has context. The organization has rules. The tools contain fragments of information. Customers create exceptions. Supervisors carry escalation knowledge. Policies change. Language matters. Timing matters.

If you only look for “tasks to automate,” you miss the system that makes those tasks easy or difficult in the first place.

Agent First therefore looks at a work system through questions such as: What context must be resolved? Which rules govern the situation? How is the right information retrieved? What judgment genuinely belongs to the worker? What language is constrained? What operational action follows? What must remain visible, explainable, and overridable?

That turns AI strategy into a design problem rather than a feature-selection exercise.

The responsibility split comes before the automation map.

I use a simple distinction.

The human should own what requires humanity.Judgment, accountability, relationships, creativity, interpretation of genuinely novel situations, and the parts of a decision where human values or responsibility matter.
The system should own what software can carry better.Retrieval, memory, context assembly, rule presentation, coordination, repetitive computation, version control, and the burden of finding what the organization already knows.

This is not a rigid border. Different environments will draw it differently. The point is that the border should be deliberate.

“Human in the loop” is too vague to do that job by itself. A human can technically remain in a process while having almost no meaningful control. If the system frames the options, hides the evidence, makes the recommendation opaque, and turns the worker into a rubber stamp, the presence of a person does not automatically make the system human-centered.

Meaningful human control requires visibility, explanation, authority, and a clear understanding of what the person is still responsible for.

Retrieval is labor.

One reason organizations underestimate bad work design is that retrieval labor is easy to ignore.

The time spent searching for a policy looks small in isolation. So does opening another system, checking a note, asking a supervisor, finding the client-specific exception, or turning internal language into something customer-ready. But these actions accumulate. More importantly, they fragment attention.

When a worker must repeatedly stop the primary task in order to rebuild the decision environment around it, the organization is spending human cognition on infrastructure.

That is a design choice—even when nobody consciously made it.

The interface is part of management.

We often treat interface design as the layer that comes after the “real” operating model. I think that is backwards.

A screen determines what arrives first, what is visible, what must be remembered, what can be ignored, what looks authoritative, what requires confirmation, what gets escalated, and what the worker can override.

Those are operational decisions.

The interface therefore distributes responsibility. It can quietly force judgment downward, centralize it upward, or encode it into the surrounding system. It can create consistency without removing discretion—or remove discretion without creating clarity.

That is why product design and operating-model design cannot be separated cleanly once software becomes the environment through which work is done.

The supervisor tax is a signal.

When a frontline system leaves ambiguity unresolved, supervisors often absorb the cost. They answer repeat questions, interpret exceptions, reassure workers, correct inconsistent decisions, approve edge cases, and become the unofficial search engine for the organization.

Some of that is legitimate leadership. Some of it is unresolved system design.

I call the second category the supervisor tax: management capacity consumed because the surrounding system has not made known rules, context, or decision boundaries usable at the moment of work.

The tax is useful diagnostically. If the same question keeps climbing the hierarchy, the first response should not automatically be “train the employee again.” It should be: why does this decision still require a live human lookup?

AI should earn the right to scale.

Once the work and the responsibility split are clear, AI becomes much easier to reason about.

Now you can ask specific questions. Should AI retrieve and summarize? Should it surface the applicable rule? Should it generate language inside constrained boundaries? Should it flag an exception? Should it recommend an action? Is the decision deterministic enough to automate? What evidence must be shown to the worker? When must a supervisor be involved?

Those are better questions because they are anchored in the work.

Then test the design in a bounded environment. Establish a baseline. Measure what changes. Speed may improve while accuracy falls. Adoption may look good while supervisor interventions increase. A prototype may feel impressive while creating new ambiguity.

Scale should follow evidence, not enthusiasm.

This is not anti-AI. It is pro-responsibility.

Agent First is not an argument for keeping people in every process. It is not an argument against automation. And it is not nostalgia for a pre-AI workplace.

It is an argument that automation should remove unnecessary human burden without accidentally removing the parts of work that need human judgment, accountability, or relationship.

The opportunity of AI is not merely that machines can now do more. The opportunity is that we can redraw the work itself.

But if we want better work, we have to design for it on purpose.

My rule is simple: design the system around the human before designing the AI inside the system.

This essay is the foundational point of view behind Agent First and Agent First Consulting. The method is applied through workflow diagnostics, product and interaction design, knowledge architecture, prototypes, pilots, and operational measurement.
